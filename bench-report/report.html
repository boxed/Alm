Computation — no DOM

The benchmark above is DOM-bound, which hides the compute backend. These are pure workloads running the same Elm source through the official compiler and alm's three backends. On scalar code (recursion, float math, sorting) alm-js is neck-and-neck with elm — it emits the same shape of JavaScript. On collections it pulls away, because alm represents List as a growable vector rather than cons cells and fuses map/filter/fold into specialized loops. WasmGC goes further by storing List Int and List Float as contiguous unboxed arrays, and the native backend's numeric loops auto-vectorize.

Every entry point in the project

Reproducing any of this. dom-bench/ drives system Chrome headless through puppeteer-core in real time (no virtual clock); each figure is the median of 3 page reloads, each the median of 15 timed iterations. compute-bench/ builds each workload with all four compilers, checks they return the same result, then times the median of 25 calls after 10 warmups; the native figure subtracts a measured process-startup floor so all columns are compute-only. compile-bench/run.py times make against a real ~40k-line codebase, writing to a real file rather than /dev/null — the official compiler skips code generation entirely for /dev/null, which would flatter it by the whole back end.

Why alm gets one compile-speed row and elm gets three. alm keeps no incremental cache: every invocation recompiles the whole module graph, package sources included. The official compiler caches aggressively, so its cold, incremental and no-op times are all shown and alm's single number has to be read against all three.
